## Area notes (evidence for the PASS verdicts)

**A. Auth chain (finding area 1) — PASS.**
`buildApp.ts:85-98`: the CSRF check runs only inside `if (session)`; `resolveSession(undefined)` returns null (sessions.ts:63) for the anonymous first POST → `/auth/login` and `/auth/register` are not CSRF-gated, and both return `csrfToken` (auth.routes.ts:80,91). `SESSION_COOKIE = 'py_session'` (sessions.ts:13) matches `req.cookies['py_session']` (buildApp.ts:86). `setSessionCookie(reply, token)` → `reply.setCookie(name, value, opts)` is the correct @fastify/cookie signature with the plugin registered at buildApp.ts:59 before routes. Token format `nonce.hmac(nonce.sessionSecret)` verifies timing-safe (csrf.ts:14-24); base64url sig contains no dots so `split('.')` is safe. Fail-closed edge: stale sessionStorage token in a second tab yields CSRF_INVALID until `/auth/me` refresh — acceptable.
CSRF-exempt prefixes match real webhook paths: bots `POST /api/v1/webhooks/bots/:botId` (bot.routes.ts:303) and wordpress `POST /api/v1/webhooks/wordpress` (wordpress.routes.ts:93) both live under `/api/v1/webhooks` (buildApp.ts:91). `/api/v1/payments/callback` is GET-only (redirect route) — exempted and not mutating. No route double-registration found across routes.ts:22-45.

**B. Tenant isolation (finding area 2) — PASS.**
Sampled all six modules end-to-end: channels (`channel.service.ts:61,82,108,210,242,274`), posts (`post.service.ts:68,82,236,299,314,338`), bots (`getOwnedBot` bot.service.ts:82-91 used by every mutation; commands/keywords also tenant-filtered :409,436,487,513), wallet (`wallet.routes.ts` passes only `req.user.id`; every ledger query tenant-scoped), wordpress (`wordpress.service.ts` — sites/products strictly `tenantId`-filtered; webhook derives tenant from the site row, never from the client), admin (`admin.routes.ts` permission-gated; overview/payments/audit are intentionally global for admins; user mutations target explicit ids under `admin.users.manage`). Payments callback resolves the tenant from the **stored** payment row (payment.service.ts:214). No client-supplied `tenantId` is trusted anywhere; registration role is assigned server-side (ADR-0007) — broken only by finding 1.

**C. Schema/code parity (finding area 6) — PASS.**
Programmatic column-name diff of `app/src/db/schema.ts` vs `database/migrations/0001_init.sql`: all 41 tables present in both; zero real column mismatches (the only diff candidates were `created_at`-style columns defined via the shared `ts()` helper, schema.ts:23). Spot checks requested by the brief: `users.referral_code CHAR(12)` fits the 9-char `R+8` code (auth.service.ts:42) and is UNIQUE; `tickets.category VARCHAR(80) NOT NULL DEFAULT 'GENERAL'` (migration:567); `event_daily.day DATE` with PK `(tenant_id, day, event_name)` (migration:529-535); `sessions` has `token_hash CHAR(64)` + `csrf_secret CHAR(64)` (generated tokens are 32 chars). All integrity keys the code relies on exist: `uq_post_targets(post_id,channel_id)`, `uq_bot_events_dedup(bot_id,dedup_hash)`, `uq_referral_rewards(referral_id,reward_kind)`, `uq_ledger_ref(ref_type,ref_id,entry_kind)`, `uq_referrals_referred`, idempotency PK `(scope,idem_key)`. No drizzle name typos detected.

**D. Payment security (finding area 3) — PASS.**
`verifyAndSettle` verifies with the **stored** `payment.amountRial` (payment.service.ts:243), binds `Authority` to the created row (:218), short-circuits VERIFIED/CANCELLED/REFUNDED (:223-228), wraps everything in `runIdempotent('payment_verify', paymentId, 86400)` whose DB-unique `(scope,idem_key)` insert is the concurrency lock (idempotency.ts:33-50; duplicate → IDEMPOTENCY_IN_PROGRESS → friendly message), and performs the VERIFIED flip + `activateSubscriptionTx` (SELECT … FOR UPDATE extension base, plan.service.ts:201-222) + wallet credit / referral hook **in one transaction** (:253-265). Referral failure is fully isolated: `referralHookFirstPurchase` swallows+audits (:124-138) and duplicate rewards are absorbed by `uq_referral_rewards` (:160). Callback route never returns JSON to a browser — always 302 (finding 9 covers the missing frontend echo).

**E. Delivery pipeline (finding area 4) — PASS except 6/7.**
Atomic claim `UPDATE post_targets SET state='PROCESSING' WHERE id=? AND state IN ('PENDING','RETRYING')` (delivery.worker.ts:94-101) — a SENT target can never be claimed by the worker, BullMQ retries, or duplicate jobs; a crash after provider-send yields at-most-once (target stays PROCESSING → finding 7 for the reaper gap). Retry classification: only `TRANSIENT`/`RATE_LIMITED` retry with bounded backoff via `nextRetryDelaySeconds` (:28,286-313); non-retryable → FAILED. Outbox relay marks DISPATCHED only after successful enqueue, poisons unknown event types after 10 attempts (outbox.ts:35-66, dispatcher.ts:37). Post aggregate recompute is guarded (`refreshPostAggregate`, WHERE state IN allowed set; CANCELLED posts never resurrect). Scheduled publish claims `SCHEDULED→QUEUED` + outbox row atomically per post (scheduler.tick.ts:50-64). Re-send via UI re-publish: finding 6.

**F. Bot webhook (finding area 5) — PASS.**
Secret compare is timing-safe (`timingSafeEqualStr`, ids.ts:15-20) after a non-secret length check; POLLING-mode bots and secret-less rows are silently ignored (`ingestBotWebhook` bot.service.ts:583); dedup before enqueue via `uq_bot_events_dedup(bot_id, dedup_hash)` + `onDuplicateKeyUpdate` no-op and `affectedRows === 0` bail (:604-622) with deterministic jobId `botev:<eventId>`; route always answers `{success:true}` and swallows all errors (bot.routes.ts:302-318), rate-limited 600/min. Ultraid `update_id`/payload hash prevents provider redelivery duplicates.

**G. Persian compliance (finding area 8) — PASS.**
Greps over `frontend/src` found no user-visible English labels/headings/buttons/errors (all literal UI strings are Persian; `EVENT_FA`/`POST_STATE_FA`/state maps cover dynamic values with Persian fallbacks). `toISOString()` appears only in API payloads (PostNew.tsx:234 — correct wire format, backend `z.coerce.date()`), optimistic notification state (Notifications.tsx:50 — internal), and Analytics bucket **keys** (Analytics.tsx:132 — display goes through `faDateShort` Jalali, :235). All counters/dates route through `faDigits/faNumber/faMoney/faDate*/faRelative` (`lib/format.ts`, Intl `fa-IR-u-ca-persian`). No Gregorian date reaches the UI.

**H. Secret leakage (finding area 9) — PASS.**
Bots list returns `tokenMasked` only — `toPublicBot` never selects/exposes `tokenEncrypted`/`webhookSecret` (bot.service.ts:40-55, comment :98). Channels DTO carries status/health only (channel.service.ts:26-54). WordPress: plaintext secret returned exactly once at connect/rotate (wordpress.service.ts:47,121-128), only `secretHash` stored; `listSites` exposes `siteKey` (a public identifier) but no secret; webhook verification is timing-safe hash compare (:139-158). Admin user list exposes email/mobile — admin-only surface, by design. `.env.example` contains placeholders only (`REPLACE_WITH_…`), with an English header explaining critical vars.

**I. Deploy contract (finding area 10) — PASS except 8.**
deploy.sh: preflight (node≥22, secrets length/hex checks, MySQL+Redis pings), migration **drift abort** (applied-but-missing → exit 1, deploy.sh:139-146), guarded `rsync --delete` for the SPA (marker or empty dir, :173-186), Passenger restart via tmp/restart.txt, real `curl` health checks against /health/live + /health/ready (:237-252), no worker auto-spawn; make-release.sh excludes .git/node_modules/.env*/logs/private/storage/coverage/tmp/sqlite/pem before the gate. Worker/scheduler duplication prevention = cron `flock` + Redis NX scheduler lock EX 55 (scheduler.ts:19-24) — sound; only the deploy-time pgrep check is fake (finding 8).
